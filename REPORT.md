# Проверка key-system — 20–21 сентября 2026

> Исторический отчёт об исходной версии. После него приложение переделано для
> браузерной камеры и хостинга. Актуальные результаты: `RELEASE_REPORT.md`.

**Итог: проект не прошёл полную проверку работоспособности.** Docker-образы
собраны, интерфейс и отдельный API-экземпляр запускались; 12 HTTP-проверок
выявили ошибки валидации и контроля доступа. Основной запуск с фотографиями
не вышел в подтверждённую готовность, затем Docker Engine стал отвечать 500
и таймаутами. Команда остановки `key-system-backend-1` и тестового API отправлена,
но её завершение на момент отчёта не подтверждено. Другие контейнеры намеренно
не останавливались, Docker Desktop целиком не перезапускался.

Камера **работает нативно на проверенном Windows**: обычный OpenCV 4.11 получает
кадры через CAP_ANY/MSMF/DirectShow. В Docker видеоустройство отсутствует.
Точную причину ранее наблюдавшегося сбоя на другом окружении без его логов
установить нельзя. Исходные 14 записей SQLite сохранены без изменения.

## Архитектура и исходное состояние

React 19 / Create React App отображает сканер, модальное окно выдачи/возврата
и журнал с поиском. FastAPI предоставляет MJPEG-видео, текущий результат
распознавания, запись действий и чтение/удаление журнала. OpenCV открывает
камеру 0, face_recognition сопоставляет лица с фото из `faces`, pyzbar читает QR.
SQLite хранит только журнал действий, отдельного учёта текущих владельцев ключей нет.

В исходном проекте отсутствовали Dockerfile, Compose и список Python-зависимостей.
README интерфейса содержит стандартную инструкцию Create React App.
Вложенный Git-репозиторий интерфейса уже имел пользовательские изменения.
Прикладной код и исходные данные при проверке не изменялись.

Исходная база: `PRAGMA integrity_check` → `ok`; 14 записей.
SHA-256: `F870CCA5F7112E331B93DEC79A3010072C43DAA0ECC296345BC1FE87FCD8E609`.

## Добавлено для запуска

- `compose.yaml`, Dockerfile и `.dockerignore` для обоих компонентов.
- `back-end/requirements.txt` с версиями основных зависимостей.
- `DOCKER.md` с командами запуска и ограничениями.
- `docker-check.py` для HTTP-проверок на отдельной тестовой базе.

Порты: интерфейс 3000, API 8081, только loopback. Порт 8000 уже занят другим проектом.
Адрес API меняется только в Docker-сборке интерфейса. База создаётся в отдельном
томе; исходный файл SQLite не подключён.

## Замечания по коду

1. **Высокая важность: доверие данным клиента.** `back-end/server.py:131–146`:
   имя, кабинет и действие берутся из JSON без сверки с распознаванием,
   без проверки существования кабинета и без списка допустимых действий.
   Требуется серверная проверка распознанной сессии и типов полей.
2. **Высокая важность: отсутствие разграничения доступа.**
   `/api/logs`, `/api/confirm-action`, `/api/clear-logs` не требуют авторизации.
   `back-end/server.py:156–161` удаляет весь журнал без возможности восстановления
   через приложение. Диалог подтверждения есть только в интерфейсе.
3. **Некорректные JSON-типы не обрабатываются.** `server.py:131–134` вызывает
   `.get()` без проверки типа тела, а значения передаются в SQLite без схемы.
   Следует использовать модель запроса и возвращать 4xx для невалидных данных.
4. **Потеря камеры не отражается в API.** `server.py:62–69`: при ошибке чтения
   поток завершается без изменения статуса и без повторного подключения.
   Последние распознанные значения также не сбрасываются при обрыве.
5. **Риск повторного открытия окна и дублирования действий.**
   `front-end/src/App.js:20–29,36–40,50–53,64–67`: закрытие окна снова включает
   опрос, и неизменившаяся пара «лицо + кабинет» снова открывает окно.
   Нет идентификатора сканирования, подтверждения потребления события и защиты
   кнопок от повторной отправки. Вывод по коду, сценарий с камерой не воспроизведён.
6. **Общий объект камеры для всех клиентов.** Каждый запрос `/video_feed`
   запускает отдельный цикл чтения одной камеры и обновляет общий `system_state`.
   Работа нескольких клиентов требует отдельной проверки и единого фонового
   производителя кадров. Нагрузочная проверка не выполнялась.
7. **Адрес сервера зашит в интерфейс.** `App.js:17,21,44,72,106` использует
   `localhost:8000`: при открытии с другого компьютера запросы идут на тот
   компьютер. Docker-конфигурация адаптирована только для локальной проверки.
8. **Устаревший тест.** `front-end/src/App.test.js:4–7` ищет `learn react`,
   отсутствующий в реальном интерфейсе. Тест не проверяет функции системы ключей.
9. **Нет проверки последовательности операций.** Сервер записывает повторную
   выдачу и возврат без предшествующей выдачи; это журнал, а не контроль наличия
   ключей. Если требуется такой контроль, нужна модель состояния ключа.
10. **Сбой API выглядит как пустой журнал.** Во время сборки сервера интерфейс
    открылся и показал «Сәйкес жазбалар табылмады», хотя API ещё не был запущен.
    `App.js:31–32` выводит ошибку только в консоль. Нужны видимые состояния
    загрузки и ошибки; иначе пользователь не отличает отсутствие записей от сбоя.

## Проверки выполнения

Подтверждено:

- Оба Docker-образа собраны. HTTP API проверен в отдельном контейнере
  `key-system-api-check` с пустой временной базой, без исходных записей.
  Все 12 результатов сохранены в `api-results.jsonl`.
- `/api/status` и `/api/logs` отвечают HTTP 200. Выдача и возврат записываются,
  журнал возвращает записи в обратном порядке ID.
- Поддельное имя `DOCKER_TEST` и действие `arbitrary-action` приняты с
  `status: success`, хотя статус распознавания был пустым.
- JSON-массив вместо объекта → HTTP 500, `AttributeError: 'list' object has no attribute 'get'`.
  Объект вместо строки имени → HTTP 500, `sqlite3.ProgrammingError`.
- Пустой JSON возвращает `status: error`, но HTTP-код остаётся 200.
- Удаление без авторизации успешно; после него журнал пуст.
  Проверка удаляла только созданные тестовые записи в отдельном контейнере.
- `/video_feed` без камеры возвращает HTTP 200 и **0 байт**.
  В основном Linux-контейнере список `/dev/video*` пуст.
- Тестовый QR-код `DOCKER-TEST-101` декодируется как в обычном виде,
  так и после зеркального отражения, используемого приложением.
- **Проблема запуска с фотографиями:** основной сервер остаётся в инициализации
  и не отвечает на `/api/status` в пределах 10 секунд. Код загружает и кодирует
  все фотографии синхронно до запуска Uvicorn. Дополнительная проверка кодирования
  лиц также не завершилась; её остановка запрошена, чтобы освободить ресурсы.
  При этом Docker Engine начал возвращать HTTP 500 на `docker top`, а HTTP
  интерфейса также стал недоступен по таймауту. Доступная память Docker около
  1,8 ГБ. Связь с ресурсами вероятна, но факт OOM по журналу не подтверждён.
  Полноценную готовность основного экземпляра с исходными фотографиями
  **подтвердить не удалось**. Результаты API относятся к отдельному экземпляру
  без загрузки фотографий. Это не означает, что вся система работает.

- Production-сборка React успешна. Предупреждение ESLint:
  `App.js:40:6`: отсутствует зависимость `fetchData` у `useEffect`.
- Nginx в Docker отдаёт интерфейс с HTTP 200 на http://localhost:3000.
  В браузере открываются сканер и вкладка журнала.
- Существующий тест выполнен в Docker: **1 тест, 1 ошибка**.
  `Unable to find an element with the text: /learn react/i`.
- Локальный `npm test` не запускается из имеющегося `node_modules`:
  `react-scripts is not recognized`.
- Исходная SQLite-база проверена повторно: SHA-256 не изменился.
- Первая сборка backend с компиляцией dlib была остановлена из-за чрезмерной
  длительности. Docker выделено около 1,8 ГБ RAM; у компилятора наблюдался swap.
  Попытка установки `python3-dlib` из Debian bookworm не удалась: пакет отсутствует.
  Для Docker выбран готовый `dlib-bin==19.24.6` из PyPI (сторонняя сборка dlib).
  `face-recognition` устанавливается отдельно с `--no-deps`; его зависимости
  перечислены явно. Имя дистрибутива `dlib-bin` отличается от ожидаемого `dlib`,
  поэтому `pip check` сообщает `face-recognition 1.3.0 requires dlib, which is not installed`, несмотря на наличие
  рабочего Python-модуля. Для строгой проверки метаданных потребуется сборка
  официального dlib в окружении с достаточными ресурсами.

## Камера: Windows, macOS и Docker

В `server.py:62` используется `cv2.VideoCapture(0)`. Камеру открывает сервер,
а не браузер: в React только `<img src=".../video_feed">`, вызова
`getUserMedia` нет. Разрешение камеры для браузера такую архитектуру не исправит.

На проверяемом Windows устройство `USB2.0 VGA UVC WebCam` имеет статус `OK`.
Общее системное разрешение камеры: `Allow`. В текущем системном Python 3.14
не установлены cv2, face_recognition, pyzbar и FastAPI; нативный Python-сервер
на момент диагностики не запущен.

В отдельном окружении `.camera-check` установлен OpenCV. Скрипт
`camera-check.py` не сохраняет и не передаёт изображения, проверяет только
открытие устройства и получение кадра.

Прогон OpenCV 5.0.0.93 и повторная проверка на OpenCV 4.11.0.86:

| Режим | Открытие | Кадр |
|---|---|---|
| CAP_ANY | Да | 640×480 |
| CAP_MSMF | Нет | Нет |
| CAP_DSHOW | Да | 640×480 |

Важно: в проверенной headless-сборке 4.11 `hasBackend(CAP_MSMF)` возвращает
`False`, DirectShow — `True`. Поэтому отказ MSMF в этой проверке объясняется
отсутствием бэкенда в пакете, а не доказанной неисправностью драйвера.
Полученные кадры доказывают работоспособность камеры на Windows. Это не
доказывает причину сбоя на другом Windows-компьютере или в другой сборке OpenCV.

Затем headless-пакет удалён из диагностического окружения и установлен обычный
`opencv-python==4.11.0.86`. Результаты сохранены в `camera-results.txt`:

| Режим обычного OpenCV 4.11 | Фактический бэкенд | Результат |
|---|---|---|
| CAP_ANY (как в проекте) | MSMF | Кадр 640×480 |
| CAP_MSMF | MSMF | Кадр 640×480 |
| CAP_DSHOW | DSHOW | Кадр 640×480 |

**Вывод:** на этом Windows неисправность нативного захвата не воспроизводится.
Media Foundation и DirectShow исправно получают кадры. Нельзя утверждать,
что проблема обязательно в MSMF или что Windows не поддерживает камеру.
Для другого компьютера нужны его окружение и лог запуска. macOS в этой
проверке недоступна, сообщение о её работе отдельно не воспроизводилось.

В Docker Linux-контейнер не имеет автоматического доступа к USB-камере Windows.
В Compose нет передачи видеоустройства. На macOS Docker также не передаёт
камеру автоматически; успешный нативный запуск на Mac не равен запуску в Docker.

Для нативного Windows стоит добавить настройку индекса/бэкенда камеры и
резервный переход на DirectShow, проверку `isOpened()` и результата `read()`,
освобождать камеру при остановке и сообщать об ошибке
через API. Для Docker переносимый вариант — получать кадры в браузере и
передавать их серверу либо использовать видеопоток с хоста. Это требует
изменения архитектуры, в рамках диагностики прикладной код не переписывался.
