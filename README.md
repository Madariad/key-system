# THPC — система учёта ключей

Камера работает **в браузере пользователя**. На сервер отправляется JPEG-кадр,
сервер распознаёт лицо и QR-код, а пользователь подтверждает выдачу или возврат.
Серверу не нужна камера, Windows-драйверы или USB passthrough.

Поддерживаются современные браузеры с `getUserMedia`: Chrome/Edge/Firefox на
Windows и macOS, Safari на macOS/iOS, Chrome на Android. Нужны камера, разрешение
пользователя и **HTTPS**. Исключение — `http://localhost` на том же компьютере.
Работа на каждой физической модели телефона не гарантируется без проверки.

## Быстрый запуск на компьютере

Установите Docker Desktop (на Linux — Docker Engine с Compose).
Откройте терминал в папке проекта:

```sh
python configure.py
docker compose up -d --build
```

Если Python не установлен, первую команду можно заменить (PowerShell/bash):

```sh
docker run --rm -v "${PWD}:/work" -w /work python:3.11-slim python configure.py
```

Откройте **http://localhost:3000**. Пароли находятся в созданном файле `.env`:

- `APP_PASSWORD` — сканирование и выдача/возврат;
- `ADMIN_PASSWORD` — сканирование и журнал, включая удаление записей.

Файл `.env` не передавайте вместе с исходниками. На новом сервере создайте свои
пароли. `configure.py` не перезаписывает существующую конфигурацию.
Первый запуск загружает базу лиц в фоне; прогресс виден на странице.
Кнопка камеры запрашивает разрешение только после нажатия. При уходе со страницы,
переключении вкладки приложения или скрытии браузера камера освобождается.

## Размещение на хостинге с Docker

Нужен **Docker/Linux-хостинг с постоянным диском**, а не статический HTML/PHP-only
хостинг. Проверяемый образ рассчитан на Linux x86_64; Compose задаёт amd64
и на Apple Silicon использует эмуляцию Docker. Практический стартовый размер сервера: 2 vCPU и 2 ГБ RAM, желательно
4 ГБ для сборки и запаса. Один экземпляр приложения, один Python worker.

1. Загрузите исходники с корневым `Dockerfile` в приватный репозиторий/на сервер.
2. Выберите Dockerfile в корне как способ сборки.
3. Задайте `APP_PASSWORD` и `ADMIN_PASSWORD`: разные, не менее 12 символов.
4. Задайте `COOKIE_SECURE=true` и `FORWARDED_ALLOW_IPS=*`, если платформа
   направляет трафик через свой доверенный HTTPS reverse proxy. Не публикуйте
   порт приложения напрямую в обход этого proxy.
5. Подключите постоянный диск к **`/app/data`**. Здесь SQLite и кэш лиц.
6. Укажите внутренний порт **8080** (либо платформа задаст переменную `PORT`).
7. Включите HTTPS на домене платформы или своём домене. Healthcheck: **`/healthz`**.

UI и API доступны на одном домене. Никакие IP, адреса API или порты в JavaScript
править не нужно. Переменные задаются на сервере, а не при сборке интерфейса.
`/healthz` проверяет HTTP-процесс; готовность распознавания видна после входа
в `/api/status` и на странице сканера.

## VPS: HTTPS автоматически через Caddy

Сначала создайте `.env`. Укажите в нём `DOMAIN=keys.example.com`.
DNS-запись домена должна указывать на VPS, входящие порты 80 и 443 — доступны.

```sh
docker compose -f compose.yaml -f compose.production.yaml up -d --build
```

Caddy получает и продлевает TLS-сертификат. Заходите по `https://keys.example.com`.
С телефона нельзя использовать `http://192.168…:3000` для камеры: нужен HTTPS.
На VPS не добавляйте публичный проброс 8080; приложение доступно через Caddy.

## Фотографии и данные

- Фото сотрудников: `back-end/faces/Имя Фамилия.jpg` (также PNG/JPEG).
- На фото должно быть **одно хорошо видимое лицо**. Имя файла станет именем сотрудника.
- После изменения фото пересоберите и перезапустите контейнер. Кэш автоматически
  пересчитывается по хэшу содержимого. Пропущенные фото учитываются в статусе;
  конкретная причина находится в журнале контейнера.
- Фото уменьшаются до 800 px до распознавания, JPEG декодируется с уменьшением.
  Файлы более 30 МБ или 60 мегапикселей пропускаются.
- Исходная `back-end/key_management.db` не импортируется автоматически. Для
  миграции остановите приложение, сделайте резервную копию и перенесите свою
  базу в `/app/data/key_management.db`. Таблица прежнего журнала совместима.
- Docker volume `app-data` сохраняет журнал между перезапусками. `docker compose down`
  сохраняет том; **не используйте `down -v`, если данные нужны**.
- Новые даты хранятся в UTC и отображаются в часовом поясе браузера. Старые даты
  без часового пояса показываются без переинтерпретации.
- Камерные кадры не записываются на диск. Кэш лиц и исходные фото — приватные
  данные, не публикуйте их в открытом репозитории.

## Сканирование

Войдите, дождитесь готовности базы и нажмите «Включить камеру». На телефоне
можно сменить переднюю/заднюю камеру; на компьютере — выбрать устройство.
Покажите лицо и один QR-код кабинета одновременно. Подтвердите действие за
90 секунд. Для следующей операции нажмите «Следующее сканирование» — это
исключает автоматическое повторное открытие окна на том же кадре.

Сеансы разных браузеров разделены. Имя и кабинет для записи берутся с сервера,
повторная отправка того же подтверждения не создаёт дубликат. Если сеть
оборвалась после записи, можно повторить ту же кнопку. Журнал доступен только
администратору, содержит поиск и постраничный просмотр.

Система ведёт журнал, не управляет электронным замком. Распознавание по фото
не проверяет живость человека и не заменяет строгую идентификацию. QR-коды
пока содержат текст кабинета, без отдельного реестра разрешённых кабинетов.

## Проверка и обслуживание

```sh
docker compose ps
docker compose logs --tail 100 app
docker compose restart app
```

API-тесты без камеры и без личных данных:

```sh
python -m venv .venv
# Активируйте .venv средствами своей ОС
pip install -r back-end/requirements-test.txt
cd back-end
python -m unittest -v test_server
```

Проверка интерфейса:

```sh
cd front-end
npm ci
npm test -- --watchAll=false --runInBand
npm run build
```

Для разработки `npm start` проксирует `/api` на `127.0.0.1:8080`.
Production собирается одним корневым Dockerfile и не использует dev-server.

Используется готовая сторонняя сборка `dlib-bin==19.24.6` из PyPI.
`face-recognition` установлен с явно перечисленными зависимостями через
`--no-deps`: метаданные ожидают пакет `dlib`, а модуль предоставляет `dlib-bin`.
Поэтому `pip check` сообщает о несовпадении имени зависимости. Функциональное
распознавание проверяется отдельно. При строгих требованиях к происхождению
бинарных библиотек соберите официальный dlib самостоятельно.

`REPORT.md` — исторический отчёт о **старой версии**. Результаты переделки
и фактически выполненные проверки находятся в `RELEASE_REPORT.md`.
